# 29.2BE: completed browser reservation release

This is one isolated performance-lab candidate based on 29.2BD (the AY runtime
restoration). It is not a change to staging 29.1 or production. The connector
runtime remains 0.6.60; no extension reload is needed for this transport change.

## Confirmed mechanism and narrow correction

For 38 selected states, eight browser tasks previously held eight reservations
until all eight completed. Server state capacity therefore stayed at seven in
Standard or twelve in Sales even after seven browser tasks had completed. This
is a confirmed scheduling bottleneck, not proof of the cause of every timeout.

The trial start response negotiates progressive reservation release. The client
reports the cumulative number of settled browser tasks during ordinary progress
collection. Each task enters the set only after its lookup promise settles
(including the existing connector cleanup). The queue atomically takes the
largest acknowledged count, validates it against the original reservation total,
and returns only those reservations. Duplicate and out-of-order requests cannot
inflate capacity. An unsuccessful lookup remains inconclusive; releasing its
scheduling reservation supplies no registry or identity evidence.

Older clients and non-trial servers keep the existing all-settled protocol.
The state ceilings (Standard 15, Sales 20), Sales 60-second deadline, worker
capacity, source limits, identity rules, registry parsers and status rules remain
unchanged. The queue still rejects work after cancellation/expiry. No database
schema change, environment change, new worker or state-check sidecar is added.
